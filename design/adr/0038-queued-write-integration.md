## Queued Write Integration
**Date:** 2026-05-21
**Status:** Proposed

### Decision

Decent Bench will adopt DecentDB v2.6.0 queued writes only for bounded,
self-contained app-generated write operations. The first target is
single-statement DML generated by the application, such as inline table edits,
where no explicit transaction-control SQL is required.

Queued writes will be opt-in and disabled by default. When enabled, the app will
open DecentDB with explicit write-queue options through the public Dart binding
and local gateway boundary:

- `write_queue_enabled`
- `write_queue_capacity`
- `write_queue_default_timeout_ms`
- `write_queue_max_batch`
- `write_queue_max_group_delay_us`

Imports, exports, migration, save-as, explicit user transactions, and bulk-load
style operations will remain on direct DecentDB handles unless a later ADR
changes that model with benchmark evidence.

Decent Bench will surface write-queue metrics in diagnostics and map queue
errors such as busy, timeout, canceled, queue-full, and queue-closed into
actionable UI errors.

### Rationale

DecentDB v2.6.0 provides an engine-owned queued write path with strict durable
group commit and public Dart entry points. This can improve predictable
concurrent read/write behavior without requiring Decent Bench to maintain a
custom writer dispatcher.

The queue is still a different execution model from direct writes. It rejects
explicit transaction-control SQL and has bounded admission, timeout, and
cancellation-before-run semantics. That makes it a good fit for app-generated
single-statement writes, but not for import transactions or arbitrary user SQL
by default.

### Alternatives Considered

- Keep all writes direct. This is simplest but leaves the new engine-owned
  concurrency surface unused for table-edit and future app-generated writes.
- Route every write through the queue. Rejected because imports, explicit
  transactions, and bulk operations need direct transaction control and
  predictable commit boundaries.
- Build an app-owned writer queue in Dart isolates. Rejected because DecentDB
  now owns the queue semantics and metrics at the engine layer.
- Enable queued writes globally by default. Rejected because it changes
  behavior for user-authored SQL and makes queue errors possible in places that
  currently use direct execution.

### Trade-offs

- The app gains another write path that must be tested and explained.
- Configuration and open options must remain compatible with normal direct
  execution.
- Queue errors need first-class UI handling instead of falling through as
  generic SQL failures.
- The first slice may not improve import performance, because imports should
  remain explicit direct transactions.
- Diagnostics become richer because queue metrics can be shown beside WAL and
  storage metrics.
